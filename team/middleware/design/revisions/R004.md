# R004: Revision 4, Your system + Equipment health + backfill (2026-10-12)

**Input:** the front-end hand-off (front-end SPEC Rev 8, R008; briefs B036–B038) and Decision round 4, all A. Q1: outages from Tesla's `backup_history`. Q2: capacity from recorded SoC only. Q3: the agreed contract now, with a monthly series as a later joint item. Q4: request months in UTC.

What changed (Revision 3 → 4):
- New `sites` facts (batteries, power, firmware, install date, backfill cursor), a `site_events` log and a `fleet_requests` counter, all in one migration (B039).
- `syncSite` maps 5 more `site_info` facts and logs firmware and battery-count changes.
- A pure `src/lib/health` module computes the 4 measurements from history reads.
- The fleet client counts billed requests. A worker backfill walks back to the install date inside the monthly budget. Old weather comes from Open-Meteo's archive.

Lead's choices (inside the PO's answers):
- **The snapshot loader reads the panel env**, not a `sites` column. Both containers load `.env`, so a column would add a write path for nothing.
- **Outages wait for a recorded fixture** (B040 → the PO runs `verify:tesla` → B041). Tesla's docs say "seconds" and no recording confirms the fields. CLAUDE.md §12 says verify, don't guess.
- **A backfill cursor**, not "every day complete". A day Tesla returns partially (the install day, an outage day) would otherwise be re-fetched forever.
- **Capacity from discharge swings only.** AC out matches the AC nameplate. Charge Wh includes conversion losses.
- **Swing energy uses UTC hour buckets** between the two samples, which land ~2 min past the hour. That's ≤ 2 min of misalignment per edge. Switch to 5-min intervals if the estimates prove noisy.
- **The backfill starts at today − 8**, because syncEnergy already owns the last 7 days.
- **The demo stays "learning".** Replay holds 7 days, so its health checks are null. That's honest. A multi-week demo dataset is Phase 1-D, not this milestone.
